# Architecture des passages actualisés

Le chemin local préparé est : **Horaires React → `/api/realtime/passages` Vite local → client Grand Lyon serveur → HTTPS officiel**. La préproduction statique garde le mode `realtime=disabled`, car un Web Worker ou un bundle Vite ne peut pas protéger une authentification HTTP Basic. Le GTFS théorique reste disponible indépendamment.

`server/realtime/client.ts` filtre par `id`, limite la réponse à 2 Mo, refuse les redirections, impose un timeout, déduplique les demandes simultanées et met en cache au plus 128 quais. L’intervalle minimal et le TTL sont configurables ; 60 secondes par défaut sont un **choix technique conservateur, pas un quota publié**. Les codes 401/403 arrêtent les nouvelles tentatives dans l’instance ; 429 respecte `Retry-After`. `server/realtime/mapping.ts` exige les identifiants exacts de quai, ligne, course, arrêt ultérieur et direction ; les résultats douteux sont rejetés. Le navigateur ne reçoit que des passages normalisés, jamais les identifiants Basic.

Le stockage local utilise d’abord Windows DPAPI `CurrentUser` dans `.data/realtime-credential.clixml`. Lorsque le profil nécessaire à DPAPI n’est pas chargé, un repli `.data/realtime-credential.local.json` n’est accepté qu’avec ACL NTFS restreinte au compte courant, SYSTEM et Administrateurs. Ces fichiers sont hors de `dist` et ignorés par Git. L’initialisation est unique via `npm run realtime:init` ; le script vérifie l’accès HTTPS avant d’enregistrer. Si aucun compte n’est disponible, il demande une seule fois les identifiants dans une invite locale, avec mot de passe masqué. Le backend recharge automatiquement le coffre au démarrage ; une configuration serveur `GRANDLYON_USERNAME`/`GRANDLYON_PASSWORD` est également acceptée. Aucun secret n’est envoyé à un service d’hébergement par ce mécanisme.

Un hébergement Cloudflare futur utilisera des [secrets de Worker](https://developers.cloudflare.com/workers/configuration/secrets/) à la place du coffre Windows, avec le même contrat de configuration serveur. Le plan Free documente [100 000 requêtes par jour, 10 ms de CPU par requête et 50 sous-requêtes](https://developers.cloudflare.com/workers/platform/limits/) ; cela ne valide pas encore le coût de rapprochement GTFS ni les limites de Data Grand Lyon. Aucun Worker n’a été déployé.

Les appels de la carte, des favoris et des itinéraires restent GTFS théoriques. Il serait incorrect de modifier leurs heures ou de déclarer une correspondance impossible sans mesures actualisées fiables à tous les points pertinents. Cette extension attend un échantillon réel autorisé et des essais comparatifs.
